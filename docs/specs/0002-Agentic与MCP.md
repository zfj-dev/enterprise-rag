# Spec 0002 — 单代理（ReAct）+ MCP 工具

> 词汇遵循 [CONTEXT.md](../CONTEXT.md)（拒答 / 忠实度 / 引用 / 黄金集 / 负样本）。
> 对应 [ROADMAP.md](../ROADMAP.md) 的 **P1（Agentic）**，并把 **P2b（MCP）** 合并进来一并做（理由见 Further Notes）。
> 发布目标：GitHub issue，标签 `ready-for-agent`。

## Problem Statement

作为项目作者（单人、求职中），当前问答是一条**确定性的单步管线**：问题优化 → 一次混合检索 → 重排 → 一次生成。它对"文档里直接写着答案"的问题表现良好，但对**需要多步才能回答**的问题基本无能为力：

- **需要先算再答**：例如"按这张表把三年的同比增长率算出来"，系统只会把表格原文念一遍，不会真去算。
- **需要跨来源聚合**：例如"每个知识库分别有多少文档还在处理中"，这要靠结构化查询而不是语义检索。
- **需要边查边定下一步**：例如"先看这份报表的口径说明，再据此查对应的明细数据"，单步检索无从下手。

这类问题目前要么答错，要么答不上来——而它们恰恰是"Agent 工程"岗位最常被问到的能力点。

同时，我这套**检索能力与文档/知识库元数据**目前只能通过自有 HTTP 接口使用，**无法被别的 AI 客户端直接复用**。而互操作（让 Claude Desktop / Claude Code 这类 MCP 客户端直接挂载我的工具）正是 Agent 工程岗位想看到的信号。现阶段要么自己造一套私有工具协议（没人能复用），要么放弃这条线。

## Solution

在现有确定性管线**旁边**增加一条**可选的** Agent 链路，不替换、不侵入：

- 一个**单代理（ReAct）**循环：用 LLM 在"思考 → 选工具 → 看结果"之间最多推进若干步，最后给出**带引用**的答案。
- 代理通过 **MCP（Model Context Protocol）**连接一组工具：`KbRetrieve`（知识库检索）、`SqlQuery`（文档/知识库元数据查询）、`Calculator`（算术）。
- 同一组工具**同时以 MCP server 形态暴露**，任何 MCP 客户端都能挂载复用——这既是交付物，也是"互操作"能力的证明。
- 代理产出答案后仍走现有 **1 步 self-check**（复用 `verify_claims` 的逐句来源支撑判定），维持"no source → no claim"。
- **默认链路不变**：Agent 由开关控制，关闭时行为与今天完全一致，因此演示模式与现有全部测试不受影响。

产出对应 ROADMAP 的 P1：用**同一套评测核心**（Spec 0001）对比开关前后的**事实命中率**与**延迟**变化；外加 P2b 的"MCP 可被客户端挂载"。

## User Stories

1. 作为项目作者，我想要一个**可开关**的代理链路，以便在不影响现有确定性管线的前提下试用 Agent 能力。
2. 作为项目作者，我想让代理能**自己决定调哪个工具**（而不是我预先写死流程），以便处理那些"一步答不出来"的问题。
3. 作为项目作者，我想要 `KbRetrieve` 工具，以便代理能像今天的问答一样检索知识库，并拿到**带稳定 chunk_id 与页码**的来源。
4. 作为项目作者，我想要 `SqlQuery` 工具，以便回答"每个库有多少文档 / 哪些还在处理中 / 某文档多大"这类**元数据类**问题。
5. 作为项目作者，我想要 `Calculator` 工具，以便回答"同比增长率是多少"这类**需要真算**的问题，而不是让模型心算。
6. 作为项目作者，我想给代理设一个**最大步数上限**，以便失控时能停下、不会无限循环烧钱。
7. 作为项目作者，我想让代理的答案仍然带**引用**，以便维持"可追溯原文片段"这条底线。
8. 作为项目作者，我想让代理的答案过一遍**自检**（逐句判断是否被来源支撑），以便知道这次代理是不是在编。
9. 作为项目作者，我想让代理在**检索不到依据时拒答**，而不是用模型自身知识硬答。
10. 作为项目作者，我想用**同一套评测核心**分别跑代理链路与确定性链路，以便量化"事实命中率涨了没有"。
11. 作为项目作者，我想看到代理链路的**延迟**（含每一步的耗时），以便判断多步代价是否可接受。
12. 作为项目作者，我想让代理链路**复用现有评测核心而不改评测代码**，以便两条链路可比。
13. 作为项目作者，我想让工具**只实现一份**、既能被内部代理调用、又能作为 MCP server 对外暴露，以便不写两套。
14. 作为 MCP 客户端用户，我想**挂载**这个 MCP server 并看到 `KbRetrieve` / `SqlQuery` / `Calculator` 三个工具及其输入 schema，以便在自己的 AI 客户端里直接用。
15. 作为 MCP 客户端用户，我想在调用工具前就能看到它的**描述与参数约束**，以便知道该怎么用。
16. 作为项目作者，我想让工具**不信任模型传入的参数**（尤其是权限与范围），以便模型被诱导时也拿不到越权数据。
17. 作为企业使用方，我想确认代理**无法执行任意 SQL、无法读到别人的知识库**，以便放心把它接进内网。
18. 作为企业使用方，我想确认代理**不会因为多步推理就绕过引用与拒答**，以便它仍然"问不到就说不知道"。
19. 作为面试官 / 招聘方，我想看到**代理开关前后的对比数字**，以便判断候选人是真上了 Agent 还是只加了个名词。
20. 作为面试官 / 招聘方，我想看到**别家客户端真能挂载我的 MCP server**，以便确认这是可互操作的能力而非自说自话。
21. 作为项目作者，我想在**测试里不启动真实 MCP 进程**也能验代理循环，以便测试确定性、可进 CI。
22. 作为项目作者，我想在**演示模式（Fake LLM）下**代理链路不崩、退化为单步回答，以便离线 demo 仍可用。
23. 作为项目作者，我想让代理的**每一步（工具名 / 参数 / 结果摘要）可观测**，以便坏了能定位是选错工具还是工具本身错。
24. 作为项目作者，我想让代理链路**不改变既有 API 契约**（默认关闭），以便前端与现有集成不用改。

## Implementation Decisions

### 组件边界

- **工具**：每个工具是一个独立单元，自带 MCP 规范的 `name` / `description` / `inputSchema`，实现一份、两种消费方式——**进程内直调**（测试与内部使用）与**经 MCP server 暴露**（对外）。
- **代理核心**：给定（问题、会话上下文、工具集、LLM、步数上限），跑一个有上限的 ReAct 循环，返回 `{answer, sources, steps, latency}`。它**不直接构造 LLM**、**不直接建 MCP 连接**——两者都从外部注入。
- **评测适配器**：把代理核心包装成与现有同步问答**同形**的 "问题 → 答案 + 来源" 调用，使 Spec 0001 的评测核心无需改动即可同时评两条链路。

### LLM 侧新增 tool-calling（保留既有文本流）

- 给 LLM 抽象**新增**一条"带工具对话"能力：输入 messages + 工具定义，返回 `{content, tool_calls}`。
- 既有的文本流接口**不动**，现有问答链路零影响。
- 默认（Fake）实现返回**空 tool_calls** → 代理自然退化为单步回答，演示模式与既有测试保持通过。

### MCP 传输

- 代理作为 **MCP client**，连接 **MCP server**；用官方 `mcp` Python SDK（**新增依赖**）。
- 传输默认走**本地 stdio**（单机自足、不占端口、无网络）；为"私有节点"形态预留可切 HTTP/SSE。
- server **只暴露 tools**，不做 resources / prompts（ROADMAP 只要求"暴露 1–2 个工具"）。

### 工具契约

- **`KbRetrieve`** —— 入参 `{query, top_k?}`；返回候选块 `[{chunk_id, doc_id, doc_name, page, text, score}]`。
  - **`kb_id` / `owner_id` 绝不取自模型参数**，由服务端会话上下文注入（与现有"权限在检索时下推、服务端注入"一致）。
  - 复用现有混合检索 + 重排，并复用现有的"枚举意图 / 具体编号"处理，使代理检索与普通问答同质。
- **`SqlQuery`** —— 入参是一段**受限的结构化查询描述**（目标表 + 选择字段 + 过滤 + 聚合 + 排序 + 上限），**不接受模型生成的原始 SQL**。
  - 可查对象走**白名单**：仅**文档 / 知识库元数据**（如文档名、状态、页数、分块数、所属库、时间），**不含用户凭证类字段**。
  - 强制行数上限；只读；owner 范围由服务端注入。
  - 该形状把注入面**由构造消除**，而不是靠转义或黑名单。
- **`Calculator`** —— 入参 `{expression}`；返回数值。
  - 用 **AST 白名单**求值（仅算术 / 比较 / 括号 / 有限白名单函数），**禁用 eval/exec**；出现名字绑定、属性访问、下标、导入等一律拒绝。

### 代理循环

- 有**步数上限**（默认取小值、可配）。每步：带工具定义调 LLM → 若有 tool_calls 则经 MCP 执行、把结果回灌 → 继续；无 tool_calls 即得到候选答案。
- 终止路径全覆盖：拿到候选答案 / 达上限 / 工具报错，任一路径都必须产出可返回的结果（不得抛穿）。
- **1 步 self-check**：候选答案过现有逐句来源支撑校验，覆盖率写入 trace；无来源时沿用现有 `no source → no claim` 处理。
- **可观测**：trace 记录每步的工具名、参数、结果摘要与耗时（沿用现有 per-query trace 的思路）。

### 开关与兼容

- 新增配置开关（**默认关**）。关闭时走原链路，行为与今天完全一致；既有 API 契约不变。
- Fake 模式下代理不产生工具调用、等价于一次普通生成。

### 安全

- 权限与查询范围**一律服务端注入**，不信任模型传入的任何范围参数。
- `SqlQuery` 无原始 SQL、`Calculator` 无 eval —— 二者按构造杜绝注入。
- MCP server 默认**仅本地**；对外暴露需显式配置 + 鉴权（与现有私有推理节点同思路）。

## Testing Decisions

- **好测试的标准**：只测**外部行为**（工具被调用后返回什么、循环在给定输入下产出什么），不测实现细节。
- **缝**（两处，其中端到端那处是复用）：
  1. **复用 Spec 0001 的 `answer_fn`** —— 代理链路作为它的一个实现，被同一评测核心度量，P1 不新增评测代码。
  2. **代理核心注入的 `llm` + MCP client** —— 单元测试传**脚本化 stub LLM**（先吐 tool_calls、再吐终答）与 **stub MCP client**，全程无网络、不起真实 MCP 进程、结果确定。
- **传输缝的处理**：MCP 传输本身在 **client 边界被 stub**，因此不引入真实进程依赖；这是本 spec 新增缝的代价，明确记在 Further Notes。
- **将测的模块**：
  - 三个工具的行为——`SqlQuery` 拒绝白名单外的表/字段与越权范围、强制行数上限；`Calculator` 拒绝非算术表达式（名字绑定 / 属性访问 / 下标 / 导入）；`KbRetrieve` 严格遵守服务端注入的 owner 范围。
  - 代理循环——给定脚本化 LLM 与 stub 工具，产出预期答案与预期步数；达上限时能收敛返回而非抛穿；工具报错时能降级返回。
  - 退化路径——Fake LLM（无 tool_calls）下代理等价于单步回答，不崩。
  - MCP server 的**工具可发现性**（暴露的工具名与输入 schema 契约）。
  - 评测适配器——代理链路能被 Spec 0001 的评测核心直接调用。
- **测试先例**：`tests/test_api_inference.py`（在边界类注入 stub、不联网）、`tests/test_prod.py`（无外部依赖），以及 Spec 0001 定下的"stub `answer_fn` + stub `judge_fn`、断言确定性"风格。

## Out of Scope

- 多代理 / 微调 / 多模态（ROADMAP 明确不做）。
- MCP 的 resources / prompts（只暴露 tools）。
- 把代理的中间步骤（思考 / 工具调用）**流式推给前端**。
- 改变**默认** RAG 链路的行为（代理是开关控制的旁路）。
- CRUD-RAG 基准。
- 生产级 MCP 部署加固（多租户、细粒度鉴权）——本 spec 只做到"**可被客户端挂载**"。

## Further Notes

- **为什么把 P2b（MCP）合并进来**：ROADMAP 里 P2b 本就标"优先"，且"工具只实现一份、两种消费方式"使**一次做完比拆两次更省**——先做 Agent 再补 MCP 会把工具层重构一遍。合并后顺序表等价于把 #4 的 MCP 与 #3 合并。
- **新增依赖 `mcp`**：本环境**未安装**（已核实），需加入真实/生产依赖清单并在宿主验证；沙箱内装依赖走 TUNA 镜像。
- **与 Spec 0001 的关系**：0001 的 `run_eval(goldenset, answer_fn, judge_fn)` 就是 P1 的**度量入口**——P1 不新增评测代码，只新增一个 `answer_fn` 实现；ROADMAP 的 P1 产出（事实命中 / 延迟**变化**）由此得到。
- **缝的取舍（如实记录）**：本 spec 新增了一条传输缝（MCP client 边界），与"缝越少越好、理想为 1"存在张力。选择是在 client 边界 stub，以保住单测的确定性；端到端度量则继续复用 0001 的唯一缝。
- **发布**：本环境无 `gh`，spec 先落 `docs/specs/`；作者在本机 `gh` 登录后 `gh issue create` 发布，并打 `ready-for-agent` 标签（同 0001 的处理）。

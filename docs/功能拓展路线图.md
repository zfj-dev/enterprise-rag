# 企业智能文档问答系统 · 功能拓展路线图

> 版本：2026-08-27　|　基于 v1.1 已完成（真实模式 13/13 自检全绿）
> 原则：延续"不过度设计"——每个功能标优先级、价值、预计工作量；GraphRAG/多模态/Agentic 只在"出现明确失败模式"时才做。

## P0 详细（已开始实现）

### 1. 多轮对话 + 问题优化
- 目标：`它营收呢？` → 改写为 `比亚迪的营收？`，多轮上下文不丢。
- 方案：`chat_service.prepare` 从 DB 加载该会话最近 N 条历史 → 传给 `_maybe_rewrite`（真实模式用 LLM 改写）→ 改写后的问题用于检索；历史也拼进 prompt。
- 现状：接口已留（`build_rewrite_prompt` / `_maybe_rewrite`），但 prepare 传的是空 history。本次补齐。
- 验收：同一 session 连续问两句，第二句能结合上文；单测覆盖 `_load_history` 与 prompt 含历史。

### 2. 黄金集 + 评估脚本
- 目标：让每次改动"可量化变好/变坏"。
- 方案：`backend/data/golden_set.json` 存（question, expect_keyword, expect_source）；`backend/evaluate.py` 对运行中服务跑黄金集，算**检索命中率**与**答案含期望事实率**，写 `logs/eval-report.log`。
- 后续：升级为 RAGAS（Faithfulness / Context Recall），但先用手工可读的轻量版。
- 验收：脚本跑通，报告落盘；与 selftest 同一"跑一条命令→助手读报告"模式。

## P1 详细（路线图，未实现）

### Docling / PP-Structure 接入
- 解析路由 `ParserRouter` 加 Docling（表格/版面）与 PP-StructureV3（中文扫描件/表格，OmniDocBench 榜首）分支；表格 chunk 保留整表 + 表头注入。
- 工作量大、需真机验证；与当前 PyMuPDF 并行，失败回退。

### 语义缓存（Redis）
- 相似问题（bge 向量相似度 > 阈值）直接返回缓存答案；Redis 存 `semantic:{query_hash}`。
- 需 Redis 环境；当前 docker-compose 未含 Redis，加服务 + 配置开关。

### 引用校验升级
- 用 LLM 逐句判断"论断是否被来源支撑"，输出每句的支撑/不支撑；聚合出**引用覆盖率**（可进评估）。

### pgvector 持久化
- 把 `InMemoryVectorStore` 换成 Postgres+pgvector 实现（`PgVectorStore.search` 落地），重启不丢；保留适配层。

## 面试怎么讲这套规划
- "我先做多轮 + 评估闭环（能度量才敢改），再做解析质量（表格是瓶颈），缓存/持久化是工程优化；GraphRAG/多模态我做了调研、明确有失败模式才上" —— 体现"数据驱动 + 克制"。

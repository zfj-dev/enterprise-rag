## ⚠️ 三件必须一起读的事，否则会误读

**1. 三个「忠实度」不是一回事。**

- `引用忠实度 100%` 判的是「**期望事实在不在返回的来源文本里**」—— 这是**检索侧**的事（该捞的捞到了），**不能读成「答案 100% 有据」**。
- `引用覆盖率 59%`（系统自研，逐句核验每条论断是否被来源支撑）与 `RAGAS faithfulness 70%` 才是同一件事。两种独立测法落在同一区间（59% vs 70%），**互相印证**。

**真实水平是「约六到七成的论断有来源支撑」**，不是 100%。

**2. `recall@k` 对长文档题结构性地低。** 3 道题的「正确分块」有 56~100 条，`recall@10` 上限只有 0.10~0.18 —— 那是**分母太大**，不是漏检（`hit@k` 与 `MRR` 不受影响）。

**3. 延迟的 P95 长尾很重**：重排 P95 13.6 s、首字 P95 19 s（P50 只有 5.6 s）。嵌入/重排走托管 API，网络往返是主要成本 —— 这也是 README 里「本机 GPU vs 托管」那个取舍的实测代价。

## 已知边界（不藏）

- **拒答率 36%**：`no source → no claim` 只在「**一条来源都没有**」时才拒答；RGB 的否定拒绝条目里检索到的是**噪声文档**（不是空），系统认为有依据，于是拿噪声硬答。要提升得按相关性卡（`MIN_RELEVANCE` 目前只被评测当参照读、服务端不卡），但那会误伤正常问题 —— 是个真实取舍。
- **RAGAS 忠实度 70%**：与自研覆盖率 59% 同向，都指向「论断支撑」这一环还有空间。
- **上下文压缩降幅「不适用」**：本轮是单轮跑法（每题新会话），没有可压的历史。要看降幅得设 `EVAL_MULTI_TURN=1` 重跑生成层。
- **延迟只测了 4 并发**；更高并发下的分位没测。
